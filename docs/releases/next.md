# Next release

Released notes: [v1.6.x](v1.6.md), [v1.5.2](v1.5.2.md).

## MCP cost record tools

The MCP server can now change cost records. `create_service_cost_record`, `update_service_cost_record`, and `delete_service_cost_record` manage a service's costs; `set_hardware_cost` and `delete_hardware_cost` set or remove a hardware asset's purchase cost. New read tools `get_hardware_cost` and `list_payment_methods` support them, and `get_record_history` accepts `record_type="cost_record"`. Each tool calls the existing API, so writes need an editor or admin with financial visibility (plus hardware visibility for hardware costs), cost records of archived services and hardware stay read-only, and every change is recorded in history under the token owner. Delete tools are annotated as destructive, and cost-record notes are neither returned nor set. The MCP server still cannot delete or archive services, hardware, vendors, or tags. See [MCP and AI assistants](../integrations/mcp.md).

## Close financial year

Admins with financial visibility can now close a financial year for service costs. Open **Cost Report → Close financial year** (`/costs/close-year`), pick a year up to the current one, review and edit every change, and confirm by typing the year. For year X, the close converts each active service's `estimated` cost records in X to `actual` in place, and creates one `estimated` record in X+1 per service. That record is the sum of the service's actuals in X after the conversion, with an optional uplift percentage. Archived services are skipped, budget records are ignored, and hardware costs are out of scope. No next-year record is created when the service already has a cost record in X+1 or when the amount is zero, so running the close twice for the same year is safe. Flags highlight rows to check: `estimate_with_actual` (excluded by default), `added_during_year`, `mixed_payment_methods`, and `year_not_ended`. The fiscal year is the calendar year.

Each close is recorded as a batch and listed under **Previous closes**. Reverting a batch sets its converted records back to `estimated` with their current amount and deletes the records it created, including records edited by hand after the close. Revert is blocked while a service touched by the batch is archived. Closes can chain: closing X+1 converts the estimates that the close of X created. Reverting the close of X then requires reverting the close of X+1 first, and the refusal names the later closes. Reverting the close of X+1 sets those records back to `estimated` and links them to the close of X again, so reverting X then deletes them. Every changed record appears in its history under the admin who closed or reverted the year.

Yearly cost uses the latest year with service cost records, so after a close a service's yearly cost shows next year's estimate, unless the service already has cost records in a later year. Everything built on yearly cost switches with it: the service list and detail, user seat costs, the renewal calendar, and renewal reminders; on the Dashboard, the **Renewal risk (90 days)** amount, **Top vendors by spend**, and the amounts in **Upcoming renewals**; the Cost Report's **Next 30 days** stat; the `yearly_cost` field of the MCP `list_services` and `get_service` tools; and the `yearly_cost` column of `services.csv` in the admin data export. Year-based charts and totals on the Dashboard and the Cost Report read cost records by year. They default to the current calendar year when it has cost records, else to the latest year with records, so closing last year before the current year has any records moves their default to the current year, which now holds the new estimates. For year X they count the converted records as actuals.

New admin endpoints under `/api/cost-records/close-year`: `POST /preview`, `POST /execute`, `POST /revert`, and `GET /batches`. A new read-only MCP tool, `preview_close_fiscal_year`, returns the preview for an admin token with financial visibility; closing and reverting stay in the web UI. Migration `050` adds the `fiscal_year_close_batches` table and the `rollover_batch_id`, `rollover_action`, and `rollover_created_batch_id` columns on `cost_records`; the API applies it on startup.
