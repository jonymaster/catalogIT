# v1.6.x

## MCP server (v1.6.0)

CatalogIT now includes an MCP server for AI assistants, published as the `jonymaster/catalogit-mcp` image and added as the `mcp` service in both Compose stacks. It supports local stdio and hosted Streamable HTTP at `/mcp`, calls the CatalogIT REST API with an API token, and never connects to PostgreSQL. Read tools cover services, vendors, hardware assets, and service cost records, subject to the token owner's role and visibility permissions. See [MCP and AI assistants](../integrations/mcp.md).

v1.6.1 fixes the hosted server's Uvicorn startup.

## MCP sign-in with your own OAuth provider (v1.6.2)

AI assistants that require OAuth (Claude.ai custom connectors, ChatGPT developer mode) can now connect to the hosted MCP endpoint. Configure an external token issuer in **Settings → MCP Sign-in**. CatalogIT accepts JWT access tokens signed by that issuer and maps them to existing, active users by email; tokens never create users. Cloudflare Access Managed OAuth is supported via the new `MCP_IDENTITY_HEADER` setting for the `mcp` service. See [MCP and AI assistants](../integrations/mcp.md).

The UI image now proxies `/mcp` to the `mcp` service, so a reverse proxy that routes everything to the UI container needs no extra rule. Migration `049` adds the `trusted_token_issuer` table; the API applies it on startup.

## MCP record history and audit log (v1.6.3)

Two new read-only MCP tools: `get_record_history` returns the change history of a service, hardware asset, vendor, or tag, and `list_audit_events` returns the global audit log (admin accounts only). Notes, contact details, assignees, cellular identifiers, and financial references are removed from history values, and audit log results list changed field names without their values. See [MCP and AI assistants](../integrations/mcp.md).

## Record history access checks (v1.6.3)

`GET /api/history/{table}/{id}` now applies the same permissions as the records themselves. Catalog tables stay open to any signed-in user; hardware tables need hardware visibility; cost records need financial visibility (and hardware visibility for hardware cost records); users, API tokens, sign-in and integration settings, notification settings, and standalone attachment history are admin-only. Unknown table names return `404`. Service and hardware timelines in the UI are unchanged.

## MCP write tools (v1.6.3)

The MCP server can now create and update vendors, tags, and services (`create_vendor`, `update_vendor`, `create_tag`, `update_tag`, `create_service`, `update_service`). Each tool calls the existing API, so the token owner's role decides what is allowed and every change is recorded in history under that user. Writes cannot delete or archive records, and do not touch notes, contacts, people, or financial fields. A viewer-role token keeps the connection read-only. See [MCP and AI assistants](../integrations/mcp.md).

`PATCH /api/services/{id}` is now available alongside `PUT`; both change only the fields in the request body.

## Frontend dependency security update (v1.6.4)

Resolves the open Dependabot alerts in the frontend. `axios`, `react-router-dom`, `vite`, and `vitest` are updated within their current major versions, and the lockfile now resolves every flagged indirect package (including `undici`, `js-yaml`, `postcss`, `follow-redirects`, and `form-data`) to a patched version. No configuration or migration changes.

## Admin seed fix, CI, and reproducible Python builds (v1.6.5)

- **Bootstrap admin:** on startup the API now finds the bootstrap admin by `ADMIN_EMAIL`. Before, it picked an arbitrary admin, so with more than one admin a changed `ADMIN_DEFAULT_PASSWORD` could silently never apply. The default admin is still created only when no admin exists. If `ADMIN_EMAIL` was changed after the first start, only the admin with the current `ADMIN_EMAIL` is re-synced.
- **Python lockfiles:** `backend/uv.lock` and `mcp/uv.lock` are now tracked, and the API and MCP images install from them with `uv sync --locked`. The MCP image no longer installs with `pip`, so it uses the same dependency versions as local development and CI.
- **CI:** a GitHub Actions workflow runs frontend lint, tests, and build, plus the backend and MCP test suites, on every pull request and push to `main`.
- **Frontend:** fixes for the React hooks lint rules added in `eslint-plugin-react-hooks` 7.1. Detail pages, forms, and settings pages reset their state when you switch records without an extra render. User directory searches ignore stale responses.

No configuration or migration changes.
